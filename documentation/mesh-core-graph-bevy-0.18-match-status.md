# Bevy Mesh and Core Pipeline — Epix Match Status

Reference: Bevy 0.18.0 sources in `tmp/bevy_render-0.18.0/src/mesh` and
`tmp/bevy_core_pipeline-0.18.0/src`, compared with `epix_engine/mesh` and
`epix_engine/render/core_graph` (C++23 no-modules build).

This is the source-of-truth tracker for the mesh/core-graph parity effort.
Every row is retained until it is fixed or the user explicitly accepts it as
intentional, deferred, or out of scope.

## Legend

| Status | Meaning |
| --- | --- |
| ✅ | Functionally equivalent |
| ⚠️ | Intentional divergence; rationale recorded |
| ❌ | Present but behavior or API differs; must fix |
| 🚫 | Missing; must implement |
| REVIEW | Audit incomplete; not yet a parity claim |
| N/A | Non-implementable or out of scope, only with user confirmation |

## Translation Rules

| Bevy | Epix |
| --- | --- |
| `Option<T>` | `std::optional<T>` / optional reference wrapper for borrowing |
| `Result<T, E>` | `std::expected<T, E>` |
| ECS resource and system | Epix resource and scheduled system |
| Rust iterator/slice | C++ range/`std::span` view |
| `wgpu` resource wrapper | Direct `wgpu::` resource where that is an accepted Epix convention |

## Mesh Render Asset and Allocator

| ID | Bevy entity / behavior | Epix counterpart | Status | Notes |
| --- | --- | --- | --- | --- |
| M1 | `MeshRenderAssetPlugin`: registers render asset + allocator and initializes vertex layouts | `MeshRenderPlugin` | ❌ | Epix's 2D renderer plugin now installs `MeshAllocatorPlugin` and initializes the render-world `MeshVertexBufferLayouts` alongside `MeshPlugin`, `Core2dPlugin`, and `RenderAssetPlugin<Mesh>` (the C++ counterpart of `RenderAssetPlugin<RenderMesh, GpuImage>`). Plugin composition is close but not identical because Epix batches the whole 2D renderer into `MeshRenderPlugin`; the layout store and allocator are the shared surface, so this stays ❌ only for structure/lifecycle difference. |
| M2 | `RenderMesh`: CPU render metadata, vertex-layout reference, indexed buffer metadata | `RenderMesh` (replaces `GPUMesh`) | ✅ | `GPUMesh` is removed; `RenderMesh` (`vertex_count`, `RenderMeshBufferInfo`, `MeshVertexBufferLayoutRef`, primitive topology) is the `RenderAsset<Mesh>::ProcessedAsset`. Mesh2d draw commands bind the vertex/index buffers from `MeshAllocator::mesh_vertex_slice`/`mesh_index_slice` with the interleaved layout's stride/offsets, and the pipeline cache specializes per interned layout (Bevy Mesh2dPipelineKey's layout id). Verified: 27 mesh + 189 render + text tests, plus client-area captures of mesh_rendering (1280x720, center (174,195,189) — identical to the pre-rework baseline), alpha_mask ((253,160,79)), batching ((42,42,46)), and font_image — all unchanged. |
| M3 | `RenderMeshBufferInfo` | `RenderMeshBufferInfo` | ✅ | The `Indexed { count, index_format }` / `NonIndexed` discriminator now drives the draw (`indexed()`); index format comes from the metadata, and the index buffer+range comes from `mesh_index_slice`. Non-indexed geometry draws `0..vertex_count` from the vertex slice in both mesh and text draw commands. |
| M4 | `RenderAsset<RenderMesh>`: fallible prepare with previous GPU asset and render-asset usage | `RenderAsset<Mesh>` → `ProcessedAsset = RenderMesh` | ✅ | `prepare_asset` now builds metadata only (interned layout via `MeshVertexBufferLayouts`, index info, topology) and leaves GPU allocation to `allocate_and_free_meshes` (M5); `byte_len` and `take_gpu_data` match Bevy's `RenderAsset` for `RenderMesh`. Accepted C++ adaptations: Epix keys `RenderAssets` by the source asset type (`AssetId<Mesh>`), which is the same keying as Bevy's `RenderAssets<RenderMesh>` (keyed by `AssetId<Mesh>`); Bevy's morph-image retry and `RenderAssetUsages` variants beyond `RENDER_WORLD` remain unported (morph is M8, out of scope here). |
| M5 | `MeshAllocatorPlugin` and `MeshAllocator`: slab allocation, update, free, buffer slices | `MeshAllocatorPlugin` + `MeshAllocator` | 🚫 | `MeshAllocatorPlugin` now registers `allocate_and_free_meshes` in `RenderSystems::PrepareAssets` (before `prepare_assets<Mesh>`, as Bevy does), freeing removed/modified meshes and uploading newly-extracted payloads into shared slabs; the offset-allocator-backed `MeshAllocator` (general slabs with growth+GPU-copy reallocation, `Slab::LargeObject` mapped upload, `slab_layouts`, Bevy's `allocations()` count, freed-gap reuse) is what the draw path reads slices from. Remaining divergences, all accepted/documented: Bevy's two-phase `SlabsToReallocate` frame batching is inlined into `ensure_slab_buffer` (equivalent end state, single growth per frame is not deduplicated across a frame), `general_vertex_slabs_supported` (WebGL2-only downlevel concern) is treated as always true (Vulkan-only renderer), and `extra_buffer_usages` is not plumbed. |
| M6 | `MeshAllocatorSettings` | `MeshAllocatorSettings` | 🚫 | The `MeshAllocatorSettings` type exists in `mesh` with Bevy's defaults (`min_slab_size` 1 MiB, `max_slab_size` 512 MiB, `large_threshold` 256 MiB, `growth_factor` 1.5), a defaults test, and is consumed by `MeshAllocator::allocate`/`GeneralSlab::make`/`grow_if_necessary`. Epix stores the settings on the `MeshAllocator` resource rather than as Bevy's separate `MeshAllocatorSettings` resource (the accepted C++ adaptation), so M6 is complete in behaviour while the resource split differs. |
| M7 | `MeshBufferSlice`, `SlabId`, allocation query methods | `SlabId`, `MeshBufferSlice`, `MeshAllocator` query methods | ✅ | `SlabId`, `MeshBufferSlice`, and the `MeshAllocator` query methods (`mesh_vertex_slice`, `mesh_index_slice`, `mesh_slabs`, `slab_count`, `slabs_size`, `allocations`) are backed by real offset-allocator-backed allocations and are now consumed by the mesh/text draw commands (device-verified). |
| M8 | Optional morph target extraction and `MorphPlugin` / `inherit_weights` | none | 🚫 | No morph target, `MorphPlugin`, mesh morph-weight components, or inheritance system exists in Epix. This is not yet accepted as out of scope. |

## Core Pipeline Plugin and Shared Facilities

| ID | Bevy entity / behavior | Epix counterpart | Status | Notes |
| --- | --- | --- | --- | --- |
| C1 | `CorePipelinePlugin`: installs 2D, 3D, blit, tonemapping, upscaling, OIT, mip generation, deferred-copy plugins | `CoreGraphPlugin` | ❌ | Bevy embeds the fullscreen shader, then installs Core2D, Core3D, deferred-lighting-id copy, blit, tonemapping, upscaling, OIT, and mip generation. Epix embeds the equivalent Slang shader and installs only Core2D, blit, and upscaling. The omitted plugin composition is not a harmless registration difference: Core2D currently retains an empty tonemapping graph node. |
| C2 | `FullscreenShader`: shared embedded fullscreen-triangle vertex shader and `to_vertex_state()` | `core_graph::FullscreenShader`, initialized by `CoreGraphPlugin` | ✅ | CoreGraphPlugin directly mirrors Bevy CorePipelinePlugin ownership: embeds the shared shader, installs core plugins, then initializes the render-world resource. Core2D only consumes it. Slang remains the accepted shader-language divergence. |
| C3 | `FullscreenMaterial<T>` and `FullscreenMaterialPlugin<T>`: extracted uniform component, two HDR/non-HDR pipelines, a typed view node, and explicit graph edges | `core_graph::FullscreenMaterial`, `FullscreenMaterialPlugin<T>`, `FullscreenMaterialNode<T>`, `FullscreenMaterialPipeline` | ✅ | Faithful Bevy 0.18 port of `fullscreen_material.rs`. `FullscreenMaterial` is a concept over a `ShaderWritable` component with `fragment_shader()`/`fragment_shader_source()`/`node_edges()`; `FullscreenMaterialPlugin<T>` installs `ExtractComponentPlugin<T>` + `UniformComponentPlugin<T>`, registers the embedded shader + queues paired LDR (`bevy_default` = Rgba8) / HDR (`ViewTarget::TEXTURE_FORMAT_HDR`) pipelines at `RenderStartup`, and registers a typed `FullscreenMaterialNode<T>` (ViewQuery `(ViewTarget, DynamicUniformIndex<T>)`, `post_process_write`, 3-entry bind group, `draw(3,1,0,0)`) into the declared sub-graph between tonemapping and `EndMainPassPostProcessing` (or auto-detects `Camera2d`→`Core2d` via `extract_on_add`). Acceptable C++/Epix adaptations (Bevy encase `ShaderType`+`WriteInto` → `ShaderWritable`; `ShaderRef` → source-relative shader path loaded under `embedded://`; `FullscreenMaterialLabel(type_name::<Self>())` → a dedicated `FullscreenMaterialLabel` `NodeLabel` subtype; auto-detect handles `Camera2d` only because no `Core3D` graph exists yet). The `extract.hpp` `prepare_uniform_components` had a latent `.get()`-on-`const C&` bug that this facility exposed (it only "worked" because the test probe coincidentally had a `.get()` member); fixed to push the component directly. Rebuilt no-modules (MSVC 14.52): the `examples_header_render_glfw_fullscreen_material` example compiles and renders a full-frame dark-red tint (center `(38,13,13)` on the cleared frame, verified visually) and the render suite is 190 pass (189 baseline + `FullscreenMaterial.StructuredForBevyParity`). |
| C4 | General `BlitPlugin`, `BlitPipeline`, and `BlitPipelineKey` | `core_graph::BlitPlugin`, `BlitPipeline`, and `BlitPipelineKey` | ✅ | Reusable core-graph facility now owns an embedded fragment shader, render-startup resource initialization, specialized-pipeline cache, direct-WGPU bind-group creation, and format/blend/sample specialization. Core2D's private output blit remains separately audited under C17. |
| C4a | `SpecializedRenderPipeline` / `SpecializedComputePipeline` specialize from `&self` | `render::SpecializedRenderPipeline` / `render::SpecializedComputePipeline` concepts | ✅ | Pipeline instances own `Key` and `specialize(key)`, and cache methods receive the specialization instance exactly as in Bevy. |

Phase/depth/graph details remain separately tracked under C6–C12 and C17; the actual tonemapping pipeline is C16. |
| C6 | `core_2d::graph::Core2d` and all graph node labels | `Core2dGraph`, `Core2dNodes` | ✅ | `Core2dNodes` now exposes Bevy's complete public label set. MSAA writeback, wireframe, bloom, general post-processing, FXAA, SMAA, and CAS remain labels for their owning optional plugins. The actual tonemapping node implementation is C16. |
| C7 | Binned `Opaque2d`, `AlphaMask2d`, their bin keys, and batch-set key | Binned `Opaque2D` / `AlphaMask2D`, `BatchSetKey2D`, and mesh producer | ✅ | Core2D now uses two Bevy-shaped binned phase types. The C++ `MeshAlphaMode2d` tagged union covers `Opaque`, `Mask(cutoff)`, and `Blend`; mask pipelines discard below the cutoff and retain depth writes. |
| C8 | Sorted `Transparent2d` phase item | `Transparent2D` | ✅ | Entity, main entity, cached pipeline, draw function, range, extra index, reverse-depth sorting, and the `indexed` discriminator now correspond. | C9 | `extract_core_2d_camera_phases` maintains opaque, alpha-mask, transparent phase resources | `extract_core2d_camera_phases` | ✅ | Each retained Core2D view now clears transparent items, prepares both binned phases with `GpuPreprocessingMode::None`, and removes dead view entries. |
| C10 | `prepare_core_2d_depth_textures` cached depth textures per target and MSAA samples | `prepare_core_2d_depth_textures` (Core2D) | ✅ | `prepare_core_2d_depth_textures` now runs in `Core2dPlugin` at `RenderSystems::PrepareResources`, gated on live Core2D opaque/transparent phases, and allocates depth through the shared render-world `TextureCache` with Bevy's per-output-target pooling. `ViewPlugin::ManageViews` no longer allocates depth for arbitrary cameras; `ViewDepthCache` is removed. Format, reverse-Z clear value, target size, and sample count match. |

| C11 | `MainOpaquePass2dNode` with independent opaque + alpha-mask pass work | `MainOpaquePass2DNode` | ✅ | The dedicated typed view node resolves both binned phases and records them, in order, into one deferred generated command buffer with Bevy-matching color/depth attachments and camera viewport. |
| C12 | `MainTransparentPass2dNode` clears/render transparent pass independently | `MainTransparentPass2DNode` | ✅ | A separate typed view node records the retained sorted transparent phase into its own deferred generated command buffer. WebGL-only viewport reset remains irrelevant to the forced Vulkan path. |

| C17 | Upscaling plugin, per-view pipeline, and node | `UpscalingPlugin`, `ViewUpscalingPipeline`, `UpscalingNode` | ✅ | Top-level plugin specializes the shared `BlitPipeline` per view during `Prepare`, stores the selected ID on the view, and provides a typed deferred-command node under `Core2dNodes::Upscaling`. It preserves Bevy clear color, camera-output mode, later-camera alpha blend, viewport scissor, and source-view bind-group caching. The render-world, move-only `PipelineServer` owns its PipelineCache-equivalent state directly and uses Bevy's `block_on_render_pipeline` before the node runs; the main world has a separate server for explicit main-world GPU work. Direct wgpu texture-view identity is the accepted representation difference. |
| C18 | OIT settings, buffers, resolve pipeline/node | none | 🚫 | No OIT subsystem. |
| C19 | Experimental depth mip-generation plugin and resources | none | 🚫 | No depth-pyramid/mip-generation subsystem. |
| C20 | Skybox pipeline and prepass integration | none | 🚫 | No core-pipeline skybox subsystem. |
