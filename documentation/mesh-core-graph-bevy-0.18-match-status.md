# Bevy Mesh and Core Pipeline — Epix Match Status

Reference: Bevy 0.18.0 sources in `tmp/bevy_render-0.18.0/src/mesh` and
`tmp/bevy_core_pipeline-0.18.0/src`, compared with `epix_engine/mesh` and
`epix_engine/render/core_graph` (C++23 no-modules build).

This is the source-of-truth tracker for the mesh/core-graph parity effort.
Every row is retained until it is fixed or the user explicitly accepts it as
intentional, deferred, or out of scope.

## Legend

| Status | Meaning |
| --- | --- |
| ✅ | Functionally equivalent |
| ⚠️ | Intentional divergence; rationale recorded |
| ❌ | Present but behavior or API differs; must fix |
| 🚫 | Missing; must implement |
| REVIEW | Audit incomplete; not yet a parity claim |
| N/A | Non-implementable or out of scope, only with user confirmation |

## Translation Rules

| Bevy | Epix |
| --- | --- |
| `Option<T>` | `std::optional<T>` / optional reference wrapper for borrowing |
| `Result<T, E>` | `std::expected<T, E>` |
| ECS resource and system | Epix resource and scheduled system |
| Rust iterator/slice | C++ range/`std::span` view |
| `wgpu` resource wrapper | Direct `wgpu::` resource where that is an accepted Epix convention |

## Mesh Render Asset and Allocator

| ID | Bevy entity / behavior | Epix counterpart | Status | Notes |
| --- | --- | --- | --- | --- |
| M1 | `MeshRenderAssetPlugin`: registers render asset + allocator and initializes vertex layouts | `MeshRenderPlugin` | ❌ | Bevy's asset-only plugin installs `RenderAssetPlugin<RenderMesh, GpuImage>`, `MeshAllocatorPlugin`, and render-world `MeshVertexBufferLayouts`. Epix's 2D renderer plugin instead installs `MeshPlugin`, `Core2dPlugin`, and `RenderAssetPlugin<Mesh>`; it has no allocator or shared vertex-layout resource. Plugin ownership and lifecycle do not match. |
| M2 | `RenderMesh`: CPU render metadata, vertex-layout reference, indexed buffer metadata | `GPUMesh` | ❌ | Bevy `RenderMesh` is lightweight metadata; `MeshAllocator` owns GPU buffers. Epix `GPUMesh` owns/reallocates direct wgpu vertex/index buffers, attribute binding offsets, and topology. This is a different representation and update model. |
| M3 | `RenderMeshBufferInfo` | `GPUMesh` index binding | ❌ | Bevy exposes only indexed count/format versus non-indexed metadata; draws obtain buffer/range from `MeshAllocator`. Epix keeps a private direct-wgpu index binding and uses its combined vertex buffer directly, so neither the interface nor allocation-driven draw behavior matches. |
| M4 | `RenderAsset<RenderMesh>`: fallible prepare with previous GPU asset and render-asset usage | `RenderAsset<Mesh>` | ❌ | Epix has expected-based preparation, `take_gpu_data`, and the `byte_len` estimate (Bevy `RenderAsset::byte_len` for `RenderMesh`: sum of per-vertex attribute strides × vertex count + index bytes). However, `prepare_asset` still immediately creates GPU buffers from `Device`/`Limits` (ignoring the previous asset), always returns `RENDER_WORLD`, and cannot return Bevy's morph-image retry. Bevy prepares `RenderMesh` metadata first and leaves GPU allocation to the M5 allocator, so the split still differs. |
| M5 | `MeshAllocatorPlugin` and `MeshAllocator`: slab allocation, update, free, buffer slices | none | 🚫 | Epix has no allocator resource or `PrepareAssets` system consuming `ExtractedAssets<Mesh>`. Bevy allocates/frees changed/removed mesh vertex/index payloads before `prepare_assets<RenderMesh>`, packs compatible data into growable slabs, copies resident allocations on growth, and uploads changed payloads after allocation. Epix's per-asset direct buffers cannot supply this behavior. |
| M6 | `MeshAllocatorSettings` | `MeshAllocatorSettings` (type added) | 🚫 | The `MeshAllocatorSettings` type now exists in `mesh` with Bevy's defaults (`min_slab_size` 1 MiB, `max_slab_size` 512 MiB, `large_threshold` 256 MiB, `growth_factor` 1.5) and a defaults test. It is currently **inert**: no allocator consumes it. M6 can only be marked complete together with M5 (the allocator), which is still missing. |
| M7 | `MeshBufferSlice`, `SlabId`, allocation query methods | none | 🚫 | Epix lacks Bevy's borrowed buffer-plus-element-range result, slab ID, `mesh_vertex_slice`, `mesh_index_slice`, `mesh_slabs`, `slab_count`, `slabs_size`, and `allocations`. Existing `GPUMesh::bind_to` hides its direct buffers and therefore cannot provide allocator-driven draw ranges. |
| M8 | Optional morph target extraction and `MorphPlugin` / `inherit_weights` | none | 🚫 | No morph target, `MorphPlugin`, mesh morph-weight components, or inheritance system exists in Epix. This is not yet accepted as out of scope. |

## Core Pipeline Plugin and Shared Facilities

| ID | Bevy entity / behavior | Epix counterpart | Status | Notes |
| --- | --- | --- | --- | --- |
| C1 | `CorePipelinePlugin`: installs 2D, 3D, blit, tonemapping, upscaling, OIT, mip generation, deferred-copy plugins | `CoreGraphPlugin` | ❌ | Bevy embeds the fullscreen shader, then installs Core2D, Core3D, deferred-lighting-id copy, blit, tonemapping, upscaling, OIT, and mip generation. Epix embeds the equivalent Slang shader and installs only Core2D, blit, and upscaling. The omitted plugin composition is not a harmless registration difference: Core2D currently retains an empty tonemapping graph node. |
| C2 | `FullscreenShader`: shared embedded fullscreen-triangle vertex shader and `to_vertex_state()` | `core_graph::FullscreenShader`, initialized by `CoreGraphPlugin` | ✅ | CoreGraphPlugin directly mirrors Bevy CorePipelinePlugin ownership: embeds the shared shader, installs core plugins, then initializes the render-world resource. Core2D only consumes it. Slang remains the accepted shader-language divergence. |
| C3 | `FullscreenMaterial<T>` and `FullscreenMaterialPlugin<T>`: extracted uniform component, two HDR/non-HDR pipelines, a typed view node, and explicit graph edges | none | 🚫 | No Epix `FullscreenMaterial` concept/plugin exists. In particular, no reusable facility installs component extraction plus uniform buffering, queues paired HDR/non-HDR fullscreen pipelines, renders through a typed view node, and either wires declared graph edges or dynamically selects the camera's Core2D/Core3D graph. Existing blit/upscaling code is concrete rather than this generic facility. |
| C4 | General `BlitPlugin`, `BlitPipeline`, and `BlitPipelineKey` | `core_graph::BlitPlugin`, `BlitPipeline`, and `BlitPipelineKey` | ✅ | Reusable core-graph facility now owns an embedded fragment shader, render-startup resource initialization, specialized-pipeline cache, direct-WGPU bind-group creation, and format/blend/sample specialization. Core2D's private output blit remains separately audited under C17. |
| C4a | `SpecializedRenderPipeline` / `SpecializedComputePipeline` specialize from `&self` | `render::SpecializedRenderPipeline` / `render::SpecializedComputePipeline` concepts | ✅ | Pipeline instances own `Key` and `specialize(key)`, and cache methods receive the specialization instance exactly as in Bevy. |
